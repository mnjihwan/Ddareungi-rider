# Git workflow

이 프로젝트는 Git Flow와 Conventional Commits를 사용합니다(2026-10-19 사용자 지정).

## Branches

- `main`: 배포 가능한 릴리스 이력.
- `develop`: 다음 릴리스의 통합 브랜치.
- `feature/<topic>`: `develop`에서 시작하고 검증 후 `develop`에 병합. 일반 기능 개선과 비긴급 버그 수정에 사용.
- `release/<version>`: `develop`에서 분기해 릴리스 준비 및 검증. 완료 후 `main`과 `develop`에 병합하고 `main`에 버전 태그 지정.
- `hotfix/<topic>`: 배포된 버전의 긴급 수정. `main`에서 시작하고 `main` 및 `develop`에 반영.

기능 브랜치의 이력은 `--no-ff` 병합으로 구분합니다. 공유 브랜치의 이력을 임의로 재작성하거나 강제 푸시하지 않습니다. 원격 상태를 확인하고 관련 테스트를 통과한 변경을 반영합니다.

## Commits

형식: `<type>(<scope>): <description>` (`scope`는 선택).

- `feat`: 사용자 기능 추가
- `fix`: 오류 수정
- `refactor`: 동작을 유지하는 구조 변경
- `perf`: 성능 개선
- `test`: 테스트 추가 또는 변경
- `docs`: 문서 변경
- `build`: 의존성·빌드 설정
- `ci`: CI/CD 설정
- `chore`: 기타 유지보수
- `style`: 동작에 영향 없는 코드 형식 변경
- `revert`: 이전 변경 되돌리기

하위 호환성이 깨지는 변경은 `!` 또는 본문의 `BREAKING CHANGE:`로 표시합니다. 설명은 한국어로 변경의 목적과 결과가 드러나도록 작성합니다.

예:

- `feat(search): 한영 키와 초성 검색 지원`
- `fix(search): 지역명과 상호 조합 검색 결과 유지`
- `fix(collector): 수량 누락 응답을 0대로 저장하지 않도록 처리`
- `fix(ai): 학습 시작 전 실행 환경 확인`

테스트가 기능의 정확성을 보장하는 경우 구현과 해당 테스트를 같은 커밋으로 묶습니다. 독립적인 테스트 작업은 `test:`로 구분합니다. 문서·빌드 변경은 독립적인 검토가 가능한 단위로 나눕니다.

## Existing development order

아직 반영하지 않은 로컬 구현은 다음의 개발 순서와 의존관계에 따라 기능별 커밋으로 정리합니다.

1. 프로젝트 및 빌드·실행 기반
2. 데이터 수집, DB, 실시간 수량 연동
3. 대여소 API와 기본 웹 화면
4. 지도·장소 검색·길찾기 및 UI 개선
5. 데이터 확대와 Python 오프라인 AI 실험
6. 검색 입력 보정
7. 후속 검토에서 발견한 오류 수정

모든 변경을 하나의 커밋에 넣거나 과거 날짜를 조작하지 않습니다. 각 커밋은 해당 시점의 선행 코드와 함께 빌드·검토 가능한 상태여야 합니다. 실제 과거 소스가 없는 기능 중간 상태를 임의로 만들어 역사인 것처럼 기록하지 않습니다.

통합 `Ddareungi-rider` 저장소는 프로젝트 루트를 관리하며 앱 소스는 `Ddareungi-rider/`에 있습니다. 루트의 `ai`, `scripts`, `docs`, Compose 파일도 통합 저장소에서 추적합니다. `bikeseoul_data`는 독립 저장소이자 고정 커밋을 참조하는 submodule입니다. 수집기 변경을 먼저 해당 원격에 올린 뒤 통합 저장소의 submodule 참조를 갱신합니다. 비밀키, `.env`, 가상환경, 모델·원본 데이터 및 로컬 테스트 산출물은 커밋에서 제외합니다.

첫 Git 반영은 과거 변경 스냅샷이 없는 상태에서 현재 검증된 소스를 의존관계와 개발 순서에 따라 나눈 최초 등록입니다. 검색 보정과 검토 수정은 이를 사용하는 기능 커밋에 함께 포함하며, 실제 과거 커밋을 재현한 것으로 표시하지 않습니다.
