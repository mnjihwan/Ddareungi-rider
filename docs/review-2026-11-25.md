## 확인 및 수정한 문제

### 1. 지도를 움직일 때마다 즐겨찾기 목록이 다시 로드됨 (중요)

- 위치: `mobile/src/screens/home/HomeScreen.tsx`, `mobile/src/features/station-search/model/useNearbyStations.ts`
- 원인: 즐겨찾기 조회(`useBatchStations`)의 쿼리 키에 거리 계산용 지도 중심이 들어 있습니다. 중심이 바뀔 때마다 새 쿼리가 되어 데이터가 비워졌습니다.
- 증상: 저장 탭에서 지도를 약 20m 이상 옮길 때마다 `POST /api/v1/stations/batch` 요청이 새로 나가고, 목록이 스켈레톤이나 '불러오는 중…'으로 깜빡였습니다.
- 수정: 대여소 ID 목록이 같으면 거리를 갱신하는 동안 이전 결과를 유지합니다(`placeholderData`). ID 목록이 바뀌면 이전 결과를 쓰지 않습니다. 경로 대여소 수량은 `dataUpdatedAt` 조건이 그대로라 이전 경로 수량이 새 경로에 섞이지 않습니다.

### 2. 대안 경로를 검증하지 않음 (중요)

- 위치: `mobile/src/features/route-planning/api/routeApi.ts`
- 원인: 도보 → 자전거 → 도보 구성과 구간별 좌표 2개 이상 조건을 추천 경로에만 확인했습니다.
- 증상: 서버가 구간이 부족하거나 좌표가 1개뿐인 대안을 보내면, 사용자가 대안을 골랐을 때 지도 경로선과 구간 목록(대여·반납 대여소, 구간 끝점)이 깨질 수 있었습니다.
- 수정: 모든 경로에 같은 조건을 적용합니다. 추천 경로가 조건을 통과하지 못하면 이전처럼 오류로 처리하고, 통과하지 못한 대안은 목록에서 뺍니다.
- 보완(2차 검토 B1): 이 수정은 모든 대안을 디코딩한 뒤에 검사해서, 경로선 데이터가 잘린 대안이나 대여소가 빠진 대안은 여전히 검색 전체를 실패시켰습니다. 2차 검토에서 대안마다 따로 검증하도록 고쳤습니다.

### 3. 즐겨찾기 값이 손상되면 최근 검색도 지워짐

- 위치: `mobile/src/features/saved/model/riderStorage.ts`
- 원인: 즐겨찾기와 최근 검색을 하나의 `try`에서 파싱해, 즐겨찾기 필드가 배열이 아니면 두 목록이 모두 빈 값이 됐습니다. 다음 저장 때 빈 값이 기기에 기록됩니다.
- 수정: 두 필드를 따로 파싱합니다. 한쪽이 손상돼도 다른 쪽은 유지됩니다.

### 4. 경로에 없는 선택 대여소가 '반납' 마커로 표시됨

- 위치: `mobile/src/screens/home/HomeScreen.tsx`
- 원인: 경로 모드의 마커 역할을 배열 순서(첫 번째는 대여, 나머지는 반납)로 정했습니다. 그래서 목록 끝에 붙은 선택 대여소도 반납 배지를 받았습니다.
- 수정: 경로 대여소 ID와 일치할 때만 대여·반납 배지를 붙이고, 그 밖의 대여소는 일반 또는 선택 배지로 표시합니다.

### 5. 상세 응답이 더 최신 수량을 덮어씀

- 위치: `mobile/src/screens/home/HomeScreen.tsx`, 새 파일 `mobile/src/features/station-search/model/mergeStationDetail.ts`
- 원인: 대여소 상세와 지도·목록 조회가 각자 60초 주기로 갱신되는데, 상세 응답을 갱신 시각 비교 없이 덮어썼습니다.
- 수정: 상세의 주소 등 다른 필드는 반영합니다. 수량·상태·갱신 시각·경과 시간은 `realtimeUpdatedAt`이 더 최신인 쪽을 사용합니다.
- 보완(2차 검토 B4): 갱신 시각이 없는 상세와 상태 필드가 빠진 상세에서 두 관측의 값이 섞이는 경우를 고쳤습니다.

### 6. 경로 대여소 상세를 닫아도 경로 전체로 돌아가지 않음

- 위치: `mobile/src/features/rider-map/ui/RiderMap.tsx`
- 원인: 경로 맞춤은 경로 좌표가 바뀔 때만 실행됐습니다. 대여소에 초점을 맞춘 뒤 상세를 닫으면 지도가 그 대여소에 머물렀습니다.
- 수정: 경로 개요 상태(`fitRoute`)로 돌아올 때마다 경로 전체에 다시 맞춥니다.

## 이전 병합의 웹 빌드 실패

### 증상

- `78879bb chore(git): 따릉라이더 모바일 앱 작업 통합`을 `develop`에 반영한 뒤(2026-11-20) CI의 `Web typecheck, test and build` 작업이 실패했습니다([실행 #7](https://github.com/mnjihwan/Ddareungi-rider/actions/runs/44694851210)). 같은 작업 안에서 `npm run typecheck`와 `npm test`는 통과했고 `npm run build` 단계만 실패했습니다. 백엔드, Docker 이미지, 배포 스크립트 작업은 모두 통과했습니다.
- 직전 `develop` 실행(`d45b306`, 실행 #6)은 성공했으므로 `78879bb`에서 시작된 실패입니다. 이 상태가 PR #4 전까지 이어졌고, PR #4의 첫 CI도 같은 이유로 실패했습니다.
- 오류 메시지:

  ```text
  [builtin:vite-transform] plugin `builtin:vite-transform` threw an error
  Caused by:
      Tsconfig not found expo/tsconfig.base
  ```

### 원인

- `78879bb`에서 웹 `src/lib/*.ts`의 공용 로직을 `mobile/src/shared/rider-contract/`로 옮기고, 웹은 이를 다시 내보내도록 바꿨습니다. 그래서 웹 빌드가 모바일 폴더 안의 TypeScript 파일을 직접 변환합니다.
- Vite(rolldown)는 변환하는 파일에서 가장 가까운 `tsconfig.json`을 읽습니다. 공용 계약 파일의 가장 가까운 설정은 `mobile/tsconfig.json`이고, 이 파일은 `expo/tsconfig.base`를 상속합니다.
- 웹 CI는 `Ddareungi-rider/web`에서만 `npm ci`를 실행하므로 Expo 패키지가 없습니다. 그래서 상속 대상을 찾지 못해 빌드가 실패했습니다.
- 타입 검사(`tsc`)는 웹 `tsconfig.json` 하나로 전체를 검사해 영향을 받지 않았습니다. 웹 테스트도 Node가 TypeScript 타입만 제거해 실행하므로 통과했습니다. 빌드 단계만 실패한 이유입니다.
- 모바일 `node_modules`가 설치된 개발 환경에서는 `expo/tsconfig.base`를 찾을 수 있어 재현되지 않았습니다.

### 수정

- `mobile/src/shared/rider-contract/tsconfig.json`을 추가했습니다(`85d7832 build(web): 공용 계약 코드에 독립 tsconfig 추가`). Expo를 상속하지 않는 독립 설정입니다(`strict`, `moduleResolution: Bundler`, `allowImportingTsExtensions`).
- 이제 Vite는 공용 계약 파일을 변환할 때 이 설정을 읽습니다. 모바일 `tsc`는 `mobile/tsconfig.json` 한 프로젝트로 검사하므로 중첩된 설정의 영향을 받지 않고, Metro 번들링은 `tsconfig.json`을 사용하지 않습니다.

### 검증

- 모바일 `node_modules`를 잠시 치워 CI와 같은 조건을 만든 뒤, 수정 전 같은 오류가 나는 것을 확인했습니다.
- 수정 후 같은 조건에서 웹 빌드·타입 검사·테스트(85개)가 통과했습니다. 공용 계약 폴더 단독 `tsc -p`도 오류가 없었습니다.
- PR #4의 수정 커밋에서 CI 4개 작업(웹, 백엔드, Docker 이미지, 배포 스크립트)이 모두 통과했습니다.

### 재발 방지

- 웹 CI는 모바일 의존성 없이 공용 계약 코드를 빌드하므로, `rider-contract` 폴더의 코드는 상대 경로의 다른 계약 파일만 가져와야 합니다. React Native·Expo·axios를 가져오면 웹 빌드가 다시 실패합니다.
- 2차 검토(B5)에서 CI에 모바일 타입 검사·테스트 작업을 추가했습니다. 이제 모바일 변경도 병합 전에 CI에서 확인합니다.

## 2차 검토

PR #4 병합 뒤 `develop`(`3382d4b`)의 모바일 작업과 1차 수정 6건을 extra-high 수준으로 다시 검토했습니다. 7건을 찾아 모두 수정했습니다.

### B1. 잘못된 대안 경로 하나 때문에 검색 전체가 실패함

- 위치: `mobile/src/shared/rider-contract/routeSearch.ts`, `mobile/src/features/route-planning/api/routeApi.ts`
- 원인: 1차 수정의 대안 필터가 `toRoutePlan`이 모든 대안을 디코딩한 뒤에 동작했습니다. 잘린 경로선(`decodePolyline` 예외)이나 배열이 아닌 `segments`(`TypeError`)는 필터 전에 예외를 냈습니다. 대여소 객체가 비어 있으면 화면에서 `stationName`을 읽다 오류가 났습니다.
- 수정: 공용 계약에 `toDrawableBikeRoute`·`toDrawableRoutePlan`을 추가했습니다. 경로마다 구간 순서(WALK, BIKE, WALK), 대여·반납 대여소, 경로선 디코딩, 구간별 좌표 2개 이상을 따로 검사합니다. 추천 경로가 실패하면 응답 전체를 오류로 처리하고, 실패한 대안만 뺍니다.

### B2. 웹 경로 검색이 구간 구조를 검증하지 않음

- 위치: `web/src/lib/api.ts`
- 원인: 웹 `searchBikeRoutes`는 `toRoutePlan` 결과를 그대로 썼고, 웹 `RoutePlanner`는 구간이 정확히 3개라고 가정합니다.
- 수정: 웹도 B1의 `toDrawableRoutePlan`을 사용합니다. 웹 테스트의 `searchBikeRoutes` 응답 예시는 마지막 구간 경로선이 좌표 1개(`"??"`)여서, 명세(좌표 2개 이상)에 맞는 예시로 바꿨습니다.

### B3. 상세를 열어 두면 AI 예측이 사라짐

- 위치: `mobile/src/features/forecast/api/forecastApi.ts`, `mobile/src/features/forecast/model/useStationForecasts.ts`, `web/src/components/StationDetail.tsx`
- 원인: 상세 예측 조회에 자동 갱신이 없었습니다(`staleTime` 5분만 설정). `forecastAt`은 예측 기준 시각이 10분을 넘으면 결과를 버리므로, 상세를 열어 둔 채 시간이 지나면 '예측 정보를 준비하고 있어요'로 바뀌고 다시 열 때까지 돌아오지 않았습니다.
- 수정: 앱과 웹 모두 예측 경로가 설정된 경우 1분마다 다시 조회합니다(`refetchInterval`). 앱은 조회 설정을 `stationForecastQuery`로 분리해 테스트합니다.

### B4. 대여소 상세 병합 시 서로 다른 관측의 값이 섞임

- 위치: `mobile/src/features/station-search/model/mergeStationDetail.ts`
- 원인: 갱신 시각이 없는 상세(서버에 관측이 남지 않은 `UNAVAILABLE`)는 더 오래된 것으로 판단해 목록의 수량을 남겼습니다. 상태 필드가 없는 더 최신 상세는 목록의 `STALE` 상태를 그대로 물려받아, 새 수량이 '갱신 지연'으로 표시되고 출발 버튼이 비활성화될 수 있었습니다.
- 수정: 수량·상태·갱신 시각·경과 시간을 항상 한 관측에서 함께 가져옵니다. 갱신 시각 없이 `UNAVAILABLE`을 보낸 상세는 목록보다 우선합니다. 갱신 시각이 있는 더 오래된 `UNAVAILABLE`은 목록의 최신 관측을 유지합니다.

### B5. CI에서 모바일 테스트·타입 검사를 실행하지 않음

- 위치: `.github/workflows/ci.yml`
- 원인: CI는 웹·백엔드만 실행했습니다. 웹 빌드가 모바일 공용 계약 코드를 함께 컴파일하는데도 모바일 쪽 오류는 병합 전에 확인되지 않았습니다.
- 수정: `Mobile typecheck and test` 작업을 추가했습니다(`npm ci`, `npm run typecheck`, `npm test`, Node 22). 설치 스크립트를 포함한 `npm ci`가 모바일에서 동작하는 것을 로컬에서 확인했습니다.

### B6. 1차 수정의 테스트 누락

- 위치: `mobile/src/features/station-search/model/stationQueries.ts`(신규), `mobile/src/features/rider-map/model/scenes.ts`
- 원인: 즐겨찾기 깜빡임 수정(`placeholderData`)과 마커 역할 수정에 테스트가 없었습니다. 즐겨찾기 수정은 쿼리 키 순서에 의존했습니다.
- 수정: 즐겨찾기 조회 설정을 `batchStationsQuery`로, 마커 역할 판단을 `routeStationRole`로 분리해 테스트를 붙였습니다. 즐겨찾기 테스트는 `QueryObserver`로 지도 중심이 바뀌면 같은 대여소를 유지하고 ID 목록이 바뀌면 비우는지 확인합니다. 경로 다시 맞춤(`fitRoute`)은 지도 SDK 동작이라 실기기 확인 항목으로 남깁니다.

### B7. 배포 빌드의 API 주소 설정 오류가 일반 오류 문구에 가려짐

- 위치: `mobile/src/shared/api/client.ts`, `mobile/src/features/route-planning/model/useRoutePlanner.ts`
- 원인: 배포 빌드에서 API 주소가 HTTPS가 아니면 요청 전에 '앱의 HTTPS API 주소를 확인해 주세요.' 오류가 나지만, 화면은 서버 오류 응답만 읽는 `describeApiError`를 거쳐 일반 문구를 표시했습니다.
- 수정: 설정 오류를 `ApiConfigError`로 구분하고, `describeApiError`와 길찾기 오류 처리에서 그 문구를 그대로 보여줍니다. 판단 로직은 `ensureSecureApiBase`로 분리해 테스트합니다.
