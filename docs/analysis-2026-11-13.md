## 2. 현재 구현 구조

```text
web (React 19 + Vite + TanStack Query, Kakao Maps JS SDK)
  │  /api → Vite proxy → :8080
  ▼
backend (Spring Boot 4.1 / Java 21, profile: local | infra)
  ├─ StationController ─ FindNearbyStationsUseCase ─ StationSearchPort
  │                                                   ├─ InMemoryStationSearchAdapter (local: 강남 3개 샘플)
  │                                                   └─ JdbcStationSearchAdapter (infra: MySQL station + Redis 실시간)
  ├─ PlaceSearchController ── Kakao Local REST (컨트롤러에서 직접 호출)
  ├─ RouteController ─ PlanBikeRoute ─ RouteProvider
  │                                     ├─ KakaoRouteClient (기본, 도보/자전거 공용)
  │                                     └─ OpenRouteServiceClient (routing.provider=ors)
  ├─ StatusController (/api/v1/status: sample|infra)
  └─ RealtimeStationRefreshScheduler (infra, 매분 bikeList → Redis station:realtime:{id})

bikeseoul_data (수집기, :8081, Flyway 스키마 소유)
  ├─ bikeStationMaster / tbCycleStationInfo → station
  ├─ bikeList 5분 스냅샷 → station_inventory_5m, station_history(시간 단위)
  ├─ OA-21229 OD CSV/ZIP → station_flow_5m
  └─ 이용 통계 API/CSV → station_usage, collection_run

ai (Python, 오프라인 학습·평가만. 서빙 API 없음)
```

### 2.1 요청 처리 방식

| 기능 | 처리 |
|---|---|
| 주변 대여소 | MySQL `latitude/longitude BETWEEN` bounding box → Java Haversine 필터·정렬 → Redis `HGETALL` 파이프라인으로 수량 결합 |
| 지도 영역 | 같은 방식, 영역 최대 1°×1°(서울 전체) |
| 대여소 이름 검색 | 1분 TTL 로컬 카탈로그(전체 대여소) + `KoreanSearch` 점수(초성·한영 키·오타 보정) |
| 장소 검색 | Kakao 키워드 검색 → (한영 변환 재검색) → 지하철 카테고리 검색 → (대여소명 기반 역 보완 최대 2회) → (주소 검색). 최대 6회 순차 호출 |
| 길찾기 | 출발/도착 후보 대여소 각 최대 3곳 → 도보 3 + 자전거 9 + 도보 3 = **최대 15회 Kakao 경로 호출**로 소요시간 비교 → 최적 조합 1개 반환 |
| 실시간 수량 | 백엔드가 매분 bikeList 전체(약 3,300건, 1,000건씩 페이징) 수집 → Redis Hash, TTL 5분. 만료·손상 시 `null`(0대로 간주하지 않음) |

### 3.1 공통 규약 차이

| 항목 | 명세 | 현재 |
|---|---|---|
| 성공 응답 | `success/data/meta.requestId/timestamp` | `{ "data": ... }` 만 |
| 실패 응답 | `success:false, error{code,message,details}` | `RouteException`·검증 오류는 `{code,message}`. `ResponseStatusException`(장소 검색 503/502)·미처리 예외는 **Spring 기본 에러 바디**로 형식 불일치 |
| 에러 코드 | `INVALID_COORDINATE`, `NO_AVAILABLE_ORIGIN_STATION`(422) 등 | `INVALID_REQUEST`, `NO_RENTAL_STATION`(404), `ROUTING_LIMIT`(503) 등 자체 코드. 검증 메시지에 내부 경로(`nearby.latitude`) 노출 |
| 응답 필드명 | 원천 필드명 유지 `parkingBikeTotCnt`, `rackTotCnt`, `shared`, `stationLatitude` … | `availableBikeCount`, `rackTotalCount`, `location{latitude,longitude}`, `updatedAt`. `shared` 미노출 |
| 최신성 | `realtimeStatus`(FRESH 등), `realtimeUpdatedAt`, `realtimeAgeSeconds` | `updatedAt`(수집 시각)만. STALE 구간 없이 5분 후 `null` |
| `X-Request-Id` | 없으면 서버 생성, 응답 meta 포함 | 미구현 |
| Rate Limit / CORS | API별 제한, 운영 도메인만 허용 | 미구현(현재는 Vite 프록시로 same-origin) |
| Timeout/Retry/CB | Provider별 짧은 timeout, 제한적 retry, circuit breaker | 전역 connect 10s / read 20s 하나. retry·circuit breaker 없음 |
| Provider 분리 | `PlaceSearchProvider`, `WalkingRouteProvider`, `BicycleRouteProvider`, `PredictionProvider` | 장소 검색은 컨트롤러가 Kakao를 직접 호출(“Controller는 외부 API 직접 호출 금지” 위반). 경로는 단일 `RouteProvider`가 도보/자전거 겸용 |
| DTO 정책 | Entity/Redis 객체를 응답으로 직접 반환 금지 | 도메인 record `Station`·`Plan`을 그대로 응답 |
| Geo Search | Elasticsearch | MySQL bbox + Java 거리 계산 (ES 미사용) |
| Redis 값 | 원천 필드명 유지 | `availableBikeCount` 등 변환된 필드명 |
| 이력 테이블 | `station_status_history`(station_dt_raw, source_dataset 등) | 수집기의 `station_history`(시간), `station_inventory_5m`(5분). 원천 `stationDt`·출처 컬럼 없음, `UNIQUE(station_id, station_dt)`와 `idx_station_history_station` 중복 인덱스 |
| CI/CD | GitHub Actions → ECR → EC2, OIDC | 워크플로 없음. Dockerfile만 존재(루트/`backend` 동일 파일 중복, root 사용자 실행) |
| Observability | Metrics, 구조화 로그, requestId | Actuator `health,info`만 노출 |

## 4. 이번에 적용한 성능 개선

| # | 대상 | 변경 | 효과 |
|---|---|---|---|
| 1 | `routing/KakaoRouteClient.java` | 후보 소요시간 매트릭스를 **virtual thread로 병렬 호출**(동시 6개 제한). 요청 단위 캐시를 `ConcurrentHashMap<Pair, CompletableFuture>`로 바꿔 동일 구간 중복 호출 방지. 쿼터/인증/장애 오류 시 남은 호출 취소 후 기존과 같은 코드로 실패 | 길찾기 1회 최대 15회 순차 호출 → 3개 묶음(도보 3, 자전거 9, 도보 3) 병렬. 호출당 300ms 가정 시 약 4.5s → 약 0.9s |
| 2 | `realtime/infrastructure/RedisRealtimeStationStore.java` | 대여소마다 Lua `EVAL` 1회(왕복 3,300회/분) → **`HSET`+`EXPIRE` 파이프라인**(500건 단위) | 로컬 Redis 측정 3,300건: **394ms → 40ms**. 원격 Redis(RTT 0.5~1ms)에서는 차이가 더 큼 |
| 3 | `application.yml` | `spring.threads.virtual.enabled=true` | 요청 스레드가 Redis/MySQL/Kakao I/O 대기 중 플랫폼 스레드를 점유하지 않음 |
| 4 | `application.yml` | `server.compression`(JSON, 2KB 이상 gzip) | 서울 전역 viewport(2,940개) 응답 **852,935B → 79,932B(-91%)** |
| + | `RealtimeStationRefreshScheduler`, Store | 수집 시도/성공 시각 `station:realtime:last-attempt-at`, `last-success-at` 기록(명세 21.2), 갱신 소요시간 로그 | `/status/realtime` 구현 기반 |

추가 테스트: `KakaoRouteMatrixTest` — 병렬 결과가 올바른 셀에 들어가는지, 경로 없음은 `null`, 동일 구간 재사용, 쿼터 오류 시 전체 실패·키 비노출.

## 5. 추가 성능 개선 권장 (우선순위순)

측정 환경: infra 모드 + 합성 대여소 3,300개(로컬 스텁), 단일 JVM.

| 우선 | 문제 | 근거 | 권장 |
|---|---|---|---|
| 높음 | 요청마다 MySQL + Redis 3,000여 키 조회 | viewport(2,940개) 120~250ms, 웹이 열린 탭마다 60초 주기 재조회 | 실시간 데이터는 1분에 한 번만 바뀜 → **인스턴스 내 스냅샷 캐시**(`last-success-at`이 바뀔 때만 Redis에서 재로딩). 대여소 메타데이터도 3,300행이므로 메모리 카탈로그 + 격자(geohash) 인덱스로 nearby/viewport를 O(k) 처리. MySQL·Redis가 요청 경로에서 빠짐 |
| 높음 | Redis 키 구조 | 대여소별 Hash + `HGETALL` N회 | 단일 Hash `station:realtime:v{n}`(field=stationId, value=압축 JSON) + `HMGET` 1회, 또는 버전 키 교체로 원자적 갱신 |
| 높음 | bikeList 이중 수집 | 백엔드(매분)와 수집기(5분)가 같은 API를 각각 호출. 백엔드 인스턴스를 N개로 늘리면 N배 | 수집기가 Redis까지 갱신하고 백엔드는 읽기만(명세 2장 Collector 분리). 백엔드에 남길 경우 ShedLock 등으로 단일 실행 |
| 높음 | 외부 호출 timeout이 과도 | 전역 read 20s. 병렬 15회 중 하나가 느리면 응답 20s | Kakao 클라이언트 전용 `connect 1~2s / read 3~5s`, 길찾기 전체 deadline(예: 8s), Resilience4j circuit breaker |
| 중간 | 장소 검색 순차 호출 최대 6회 | 컨트롤러 내 순차 호출 | 키워드 검색과 지하철 카테고리 검색을 병렬화, `query+반올림 좌표` 키로 Redis 5~10분 캐시(명세 22장). `PlaceSearchProvider`로 분리 |
| 중간 | 대여소 검색 CPU | 3,300개 전체에 퍼지 점수 계산, 호출마다 정규식 `matches` 재컴파일. 웜 상태 100~130ms | `Pattern` 상수화, 카탈로그 적재 시 정규화·자판 변환값 미리 계산, 초성/키 n-gram 인덱스 |
| 중간 | `searchCatalog()`가 `synchronized` | 1분마다 재적재 동안 모든 검색 요청이 대기 | 스케줄 갱신 + `volatile` 교체(무잠금 읽기) |
| 중간 | MySQL 위치 인덱스 | `(latitude, longitude)` 복합 B-tree는 앞 컬럼 범위만 활용 | 메모리 카탈로그 적용 시 불필요. DB 조회 유지 시 `POINT SRID 4326` + `SPATIAL INDEX` |
| 낮음 | 이력 테이블 중복 인덱스 | `UNIQUE(station_id, station_dt)`와 `INDEX(station_id)` | `idx_station_history_station` 제거로 쓰기 비용 감소 |
| 낮음 | 컨테이너 JVM | Dockerfile에 JVM 옵션 없음 | `-XX:MaxRAMPercentage=75`, AppCDS/Spring AOT 캐시로 기동 시간 단축, non-root 사용자 |

## 6. 추가로 구현해야 할 항목

진행 순서와 병렬 가능 여부(예측 AI 제외)는 [로드맵](roadmap-2026-11-13.md)을 따른다.

### P0 — API 계약 정합성 (공개 전 필수)
1. **공통 응답/에러 포맷**: `success/data/meta.requestId/timestamp` 래퍼, `GlobalExceptionHandler`에 `ResponseStatusException`, `MissingServletRequestParameterException`, `MethodArgumentTypeMismatchException`, `HttpMessageNotReadableException`, 일반 `Exception`(500, 내부 정보 미노출) 처리 추가. 명세 10장 에러 코드로 매핑.
2. **`X-Request-Id` 필터 + MDC** 로그 연동.
3. **실시간 최신성 필드**: `realtimeStatus`(FRESH/STALE/UNAVAILABLE), `realtimeUpdatedAt`, `realtimeAgeSeconds`. v5 제안값(FRESH 120s / STALE 제공 600s / TTL 900s)으로 Graceful Degradation.
4. **누락 엔드포인트**: `GET /stations/{stationId}`, `GET /stations/realtime`(최대 100, `notFoundStationIds`), `GET /status/realtime`(이번에 추가한 Redis 키 사용).
5. **응답 필드명 결정**: 명세(원천 필드명) 방식으로 전환하거나, 현재 필드명을 유지할 경우 명세를 개정. 웹 타입(`web/src/lib/types.ts`)과 함께 변경해야 하므로 `/api/v1` 내 breaking change 여부를 먼저 결정.
6. **길찾기 계약**: `/routes/search` 경로, `options`(검색 반경·최대 도보 거리·후보 수), `alternatives`, Encoded Polyline.

### P1 — 기능·안정성
7. **예측 API**: AI 서빙(Python) + `PredictionProvider` + `/stations/{id}/predictions`, `/timeline`, `stationId+targetAt+modelVersion` Redis 캐시. 현재 웹의 `POST /stations/forecasts` 계약과 명세 계약을 하나로 통일.
8. **Provider 분리**: `PlaceSearchProvider`(장소 검색을 서비스 계층으로 이동), `WalkingRouteProvider`/`BicycleRouteProvider`.
9. **Rate Limit**: Bucket4j + Redis, `/places/search`·`/routes/*` 강하게, 429 + `Retry-After`.
10. **Resilience**: Provider별 timeout, Timeout/5xx만 제한적 retry, circuit breaker, 수집기 bikeList retry + backoff.
11. **Readiness 구성**: `management.endpoint.health.group.readiness.include=readinessState,db,redis`, Actuator 관리 포트 분리(외부 비공개).
12. **CORS**: 운영 도메인 화이트리스트.

### P2 — 운영
13. **GitHub Actions**: test → bootJar → Docker build → ECR(SHA 태그, OIDC) → EC2 배포 + readiness 확인 후 전환.
14. **Observability**: Micrometer Prometheus, 외부 Provider 성공률/지연, 실시간 데이터 age gauge, 정확한 좌표를 남기지 않는 JSON 구조화 로그.
15. **데이터**: `station_history`에 `station_dt_raw`, `source_dataset` 추가. 명세의 OA-20447(시간대별 운영현황), OA-22382(장기 대여가능 수량) 적재기는 수집기에 없음.
16. **client-config(웹 점검 모드)**, Deprecation/Sunset 헤더.
17. **Elasticsearch**: 대여소 3,300개 규모에서는 5장의 메모리 카탈로그가 더 빠르고 단순하다. 장소 자체 색인 등 요구가 생길 때 도입하고, 명세의 ES 항목은 재검토를 권장.

### 7.3 `.env`에 넣어야 하는 키

| 변수 | 필수 여부 | 발급처 / 설정 | 없을 때 |
|---|---|---|---|
| `SEOUL_API_KEY` | infra·real 필수 | [서울 열린데이터광장](https://data.seoul.go.kr) 회원가입 → 마이페이지 → **일반 인증키 신청**. `bikeList`, `bikeStationMaster`, `tbCycleStationInfo` 등에 공통 사용 | 수집기가 기동 거부(`must not be blank`) |
| `KAKAO_MAPS_JAVASCRIPT_KEY` | 지도 표시에 필요 | [Kakao Developers](https://developers.kakao.com) → 앱 생성 → 앱 키의 **JavaScript 키**(32자리 hex). [카카오맵] > [사용 설정] ON, JavaScript 키의 SDK 도메인에 `http://localhost:5173`, `http://127.0.0.1:5173` 등록 | 지도 대신 “지도 연결을 기다리고 있어요” 미리보기, 목록·검색은 동작 |
| `KAKAO_MAPS_REST_API_KEY` | 장소 검색·길찾기에 필요 | 같은 앱의 **REST API 키**. 서버 전용(`VITE_` 접두사 금지) | `/places/*` 503, 길찾기 비활성(`/routes/status` → configured=false) |
| `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD` | infra·real 필수 | 임의 값. **MySQL 볼륨 최초 생성 시에만 적용** | Compose가 시작 거부 |
| `ORS_API_KEY` | 선택 | openrouteservice. `routing.provider=ors`일 때만 | 사용 안 함 |
| `VITE_FORECAST_API_PATH` | 선택 | 예측 API 구현 후 `/stations/forecasts` | 예측 “준비 중” 표시 |

키 값은 `.env`(Git 제외)에만 둔다. 실행 스크립트는 허용된 변수만 읽고 값을 출력하지 않는다.
